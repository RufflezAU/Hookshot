# Profile — 2026-11-13: the friend's patch set on the Deck (Hookshot, RADV, Van Gogh)

Measured on the Deck OLED docked, in Game Mode, from the live install
`/home/deck/Games/Hookshot-legacy477b` (pair `hookshot 2cd79a0f` + `hookshot_vk.so 67412404`),
plus a matched-scene A/B through `ab_harness.py` (headless, same config both sides).

Builds: the pair played for these numbers was `hookshot 2cd79a0f` + `hookshot_vk.so 67412404`;
`hookshot 68e38fec` + `hookshot_vk.so 21ed13de` is the same code with the 20 us spin and the
per-bucket alignment compiled in rather than set by `configs/stable.env`.

## 1. Where the CPU goes — share of a core per thread

From `HOS_PROFILE=10` / `HOS_THREAD_TIMES=10` in the game's own log (`prof:` lines). Three
consecutive 10 s intervals in the field with the camera moving:

| thread | share of a core (3 samples) | who |
|---|---|---|
| **OptimizeChangeBanc** (guest)  | 66 / 64 / 67 % | the game's background model-material rebuild; walks every placed object by name, ~250 k lookups a second |
| **Presentation Thread**         | 64 / 44 / 44 % | ours: the replay (recording + submit) |
| **ParallelDecompThread** (guest)| 43 / 43 / 46 % | the game's asset decompression worker |
| sead::MainThread (guest)        | 22 / 26 / 23 % | the game's main thread |
| BaseProcExecutor0..5 (guest)    | 25,21,18,20,15 … | the game's job workers |
| ModuleSystemWorker1..5 (guest)  | 19,16,16,16,15 … | the game's module/asset workers |
| NavMeshCAStepDepWorker1 (guest) | 10–13 % | pathfinding |
| aal::LowPrioWorkerThread        | 10 % | audio |
| **all threads**                 | **443 / 433 / 401 %** | |

**The machine is over-subscribed.** 4.0–4.4 cores of work on 4 physical cores (6 guest vcores
timeshared over them, SMT on). There is no idle core, which is why every millisecond taken off
the frame shows up as frame rate and why the frame is CPU-bound while the GPU idles: `GPU time`
is 5.8–12.1 ms against a 36–58 ms frame.

The single largest consumer is a **guest background thread**, not the renderer: `OptimizeChangeBank`
at two thirds of a core. We already demote it to lowest priority (`hos_thread.c`; measured before
as 17–20 fps at normal priority vs 21–28 at lowest), but lowest on POSIX is nice 19, which still
gets scheduled. It is the obvious next lever: `SCHED_IDLE` (or a duty-cycle cap) would take most
of that 0.6 of a core away from the frame's threads.

## 3. Matched-scene A/B, build only (harness, same config both sides)

Both sides at 704/706 draws, 102/104 dispatches, 141/147 passes, 157/156 barriers, 80/80 uniform
updates; 67 and 70 samples:

| ms, median | base pair | patched | Δ |
|---|---|---|---|
| replay | 19.19 | **14.26** | −4.93 (−26 %) |
| frame | 45.25 | **36.23** | −9.02 (−20 %) |
| guest (frame − replay) | 26.06 | 21.97 | −4.09 |
| fps | 22.1 | **27.6** | +25 % |

This is the cleanest number we have: same scene, same inputs, one binary apart. It isolates the
patch, and it shows both halves of the frame improving, so nothing is being borrowed from the
other side.

**One finding worth keeping**: the friend's own default for the SVC release spin (64 pauses, ~1 µs)
costs about 9 ms a frame on this APU — with it, the same build measured 45.25 → 44.74 ms (no gain
at all). At the 20 µs this build has always used, it is 45.25 → 36.23 ms. That default is now 20 µs
in `host/hos_svc.c` as well as in `configs/stable.env`.

## 4. What the frame log / stack sampler would add (not captured yet)

`HOS_SAMPLE_ALL` and `RX_VK_FRAMELOG` carry **paths**, and `hookshot_env.txt` deliberately refuses
anything with a path in it — it is a file players pass around. So the first run captured the thread
shares above but not the stacks or the per-frame pictures. Both are now exported by the launcher
(`hookshot-legacy477b-play.sh`) instead.

With one more launch they give:

- **frame by frame**: `RX_VK_FRAMELOG` writes `u64 ns, u32 seq, u32 kind (game/made), 320x180 RGBA`
  per presented frame — the interval series, p50/p95/p99, the worst individual frames, and
  `scripts/framelog.py`'s one-frame flash scan (brightness against *both* neighbours, 20x20 blocks).
  Its capture copies 320x180 off each presented image, so treat its fps as "with recording on".
- **CPU cycles by function**: `HOS_SAMPLE_ALL` samples every guest thread and the renderer's every
  2 ms; `scripts/cpu_report.py` reports by category, thread and function, resolved with this
  build's own maps (`hookshot.map`, `hookshot_vk.so.map`, both from the 19:19 link that produced
  the installed binaries).

```sh
# reproduce (the gates are what start and stop the capture)
touch /home/deck/hs/prof/all.go /home/deck/hs/prof/frames.bin.go    # start
rm -f  /home/deck/hs/prof/all.go /home/deck/hs/prof/frames.bin.go   # stop
RX_MAPS=/home/deck/Games/Hookshot-legacy477b \
  python3 scripts/cpu_report.py /home/deck/hs/prof --out report.md
```

## 5. Config that matters on this APU

- `HOS_SPIN_US=20` — the SVC release spin. Not 1 µs (see §3). Now the code default too.
- `RX_VK_FRAMEGEN=0` — at 2x it cost 8.5 ms of GPU time a frame and doubled shadows/ghosting.
- `RX_VK_CHECKPOINTS=0` — it wrote a `VK_AMD_buffer_marker` before **every** draw and dispatch,
  ~2 300 a frame. Diagnostic only.
- `RX_VK_VRAM_MB=2800`, `RX_VK_TEX_MAX_MB=256`, `RX_VK_TEX_MAX_DIM=1024` — as measured before.
